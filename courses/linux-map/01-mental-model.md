This course teaches **awareness, not syntax**. For each thing you'll learn *what it is*, *what problem it solves*, *what class it belongs to*, and *the words to say* so you (or an AI) can go and do it.

## Two worlds

Linux runs code in two modes:

| | **User space** | **Kernel space** |
|---|---|---|
| who | your programs: shells, browsers, trading engines | the kernel: one big privileged program |
| can touch hardware? | no | yes |
| how it asks for things | **system calls** | — |

A **system call** (syscall) is the doorway: `read`, `write`, `open`, `mmap`, `clone`, `epoll_wait`… About 300–450 of them depending on architecture. Every file read, network packet and new process goes through one. Crossing the doorway costs time (a context switch into the kernel) — which is why low-latency finance works so hard to **avoid syscalls on the hot path**.

```viz syscall
> Each red notch is a trip across the privilege boundary. Turn up the I/O rate and watch how much time goes to crossing. Kernel bypass removes the notches entirely.
```

```choice
? A trading program wants to send a packet. Which is true on a normal Linux box?
- [ ] It writes directly to the network card's registers // Not allowed from user space — unless you deliberately use kernel bypass (later lesson).
- [x] It makes a system call (e.g. send) and the kernel drives the network card // The kernel owns the hardware.
- [ ] It asks the shell to send it // The shell is just another user-space program.
> User programs can't touch hardware; they ask the kernel via syscalls. Kernel bypass is the special exception HFT uses.
```

## Everything is a file

Unix's big idea: most things are exposed as **files you can read and write** — including things that aren't files at all.

- `/dev/…` — devices (disks, terminals, `/dev/null`)
- `/proc/…` — live info about processes and the kernel (`/proc/cpuinfo`, `/proc/<pid>/status`)
- `/sys/…` — kernel objects and knobs (CPU frequency, **cgroups** at `/sys/fs/cgroup`)
- sockets, pipes — also handled through **file descriptors**

So the "API" of many kernel features is literally: *write a number into a file*. Remember that — it's how cgroups work.

```steps How would you find how much memory a process uses?
You don't need to know the tool. Think: "everything is a file" and "/proc has live process info".
---
Every process has a directory `/proc/<pid>/`.
---
Inside, `status` has human-readable fields like `VmRSS` (resident memory).
---
So: read `/proc/<pid>/status`. Tools like `ps`, `top` and `htop` are just pretty readers of `/proc`.
```

```answer
? Which directory holds live, per-process information that tools like ps and top read from?
= /proc
= proc
= /proc/
hint: It's a virtual filesystem named after "processes".
> /proc is generated by the kernel on demand; nothing is stored on disk.
```

## The layers, top to bottom

```viz stack packet=read()
Your command or program | e.g. <code>cat notes.txt</code> or a trading engine
C library (glibc) | turns <code>fopen()</code> into the raw <code>openat</code> / <code>read</code> syscalls
System call interface | the one doorway: a special CPU instruction switches to kernel mode
Kernel | scheduler, memory manager, VFS, network stack, drivers
Hardware | CPU, RAM, NVMe disk, network card
> Press send to watch a <code>read()</code> travel all the way down to the disk and back.
```

```order
? Order from what you touch to what touches the hardware.
1. Your command or program
2. The C library (glibc) wrapping syscalls
3. The system call interface
4. The kernel (scheduler, memory manager, drivers)
5. Hardware (CPU, RAM, network card)
> Almost every question in systems work is "at which layer is the time/problem?"
```

```reflect
? Explain to a friend why a system call is "expensive" and why that matters for high-frequency trading.
- mentions switching from user mode into kernel mode
- mentions it's done on every I/O operation
- connects to latency: fewer/no syscalls on the critical path
model: A syscall is a hand-off from your program to the kernel. The CPU switches privilege mode, the kernel does work, then switches back — hundreds of nanoseconds to microseconds each time. When your edge is measured in microseconds, you design the hot path to avoid them.
```

```recall The one mental model
? User space, the kernel, and the doorway between them.
Programs run in user space; the kernel owns the hardware. A system call is the doorway between them. Everything is a file, and a file descriptor is a small integer naming an open file, socket or pipe.
```

```cards
System call :: The doorway from user programs into the kernel (read, write, mmap, clone…).
User vs kernel space :: Programs vs the privileged core that owns the hardware.
/proc :: Virtual filesystem of live process and kernel info.
/sys :: Virtual filesystem of kernel objects and tunables (incl. cgroups).
File descriptor :: A small integer naming an open file, socket or pipe.
